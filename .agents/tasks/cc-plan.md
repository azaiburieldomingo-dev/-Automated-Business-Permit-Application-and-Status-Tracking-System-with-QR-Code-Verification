# Implementation Plan — Applicant Control-Center Portal (CC)

Municipality of Bansud Business Permit System · Laravel 13 / PHP 8.3 / SQLite · timezone Asia/Manila · manual GCash payment mode.

Laravel root for ALL commands: `"c:\Users\HP\BUSINESS PERMIT_SYSTEM\app"` (the `app` subfolder IS the Laravel root; the parent path contains a SPACE — always quote paths). Test command: `php artisan test` run with cwd `"c:\Users\HP\BUSINESS PERMIT_SYSTEM\app"`. **Baseline to protect: 154 passed / 519 assertions, GREEN.**

This plan implements the approved design `cc-design.md` (iteration 5). It does NOT re-decide architecture; every item sequences the design's locked decisions. Order is by dependency: config/nav/routes scaffolding first, then the two new backend flows (Business Profile, Settings), then the dashboard overhaul that depends on the eager loads, then Help and the payment-flash fix, then the full test gate.

## Hard-correctness constraints (reaffirmed — every item must respect these)

1. **Nine statuses only**, via `Application::STATUS_*` constants and `<x-status-badge>`. No invented labels ("Paid"/"For Payment"/"Released").
2. **Payment is verified by the TREASURER, not BPLO.** All "who verifies" copy comes from the `<x-process-tracker>` step table (`STATUS_PAYMENT_PENDING => 'Treasurer'`), never from the stale `Payment::isAwaitingVerification()` docblock or the `config/permit.php` comment.
3. **Single source of truth = `applications.status`** (the same column staff update). Correction/rejection reasons read from `ApplicationRemark` (`type` literal `'CORRECTION'`/`'REJECTION'`, column `body`) and `ApplicationStatusHistory.note`. No second status store.
4. **Fees only from `FeeComputationService::computeFor()` or a persisted `Payment` row; never hard-coded; never shown before `APPROVED_FOR_PAYMENT`** in lifecycle order.
5. **Action-Required derives from STATUS**, not `read_at` (the dashboard marks notifications read on load).
6. **Permit + QR stay gated**: links render only when `status === PERMIT_RELEASED` AND the eager-loaded `permit` relation is non-null; the existing route `abort_if`/policy guard is untouched.
7. **Theme scope unchanged**: homepage/login/register/auth stay DARK and are NOT edited. New/changed views extend `layouts.app` (light `body.has-sidebar` theme) and reuse existing components/classes only.
8. **Role NEVER mass-assignable**: new controllers follow `Auth\RegisterController` (`$user->fill([...safe fields...])`; `role`/`is_active` never in a FormRequest or `fill()`). New business `user_id` set via `associate()`, never mass-assigned.
9. **Backward compatibility**: `applications.business_id` stays nullable; existing `business_id = null` applications keep working; `ApplicationFlowTest` must stay green.
10. **Renewal R1 adds NO `application_type` column and no schema change anywhere.** Reminder is read-only logic over `permit.valid_until`.
